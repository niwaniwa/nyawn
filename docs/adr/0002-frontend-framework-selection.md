# フロントエンドフレームワーク選定

## コンテキスト

プロフィールカード作成サイトのフロントエンド技術を選定する必要がある。以下の制約がある:

- ユーザー認証なし・バックエンド不要のクライアントサイド完結SPA
- リアルタイムプレビュー付きのカードエディタが主要機能
- localStorageでデータを永続化
- 「簡単に、モダンに、かわいく」を実現するUI開発の生産性

## 検討した選択肢

### 選択肢 A: Vite + React

- 利点:
  - 高速なビルド・HMR による快適なDX
  - React エコシステムが豊富（カードレンダリング系ライブラリとの親和性が高い）
  - SPAに不要なSSR/SSGの複雑さがない
  - Zustand 等の軽量状態管理との組み合わせが容易
- 欠点:
  - ルーティングを自前で設定する必要がある（React Router）
  - SEOが弱い（SPAの宿命だが、本プロダクトでは問題にならない）

### 選択肢 B: Next.js

- 利点:
  - SSR/SSG対応でSEO面が強い
  - ファイルベースルーティングが便利
  - 将来的にAPI Routes でバックエンドを追加しやすい
- 欠点:
  - MVPにはオーバースペック（SSR/SSG/ミドルウェア等を使わない）
  - ビルド・デプロイの複雑さが増す
  - 不要な機能分の学習コスト・依存が増える

### 選択肢 C: Astro

- 利点:
  - コンテンツサイトに強い。ゼロJSデフォルト
  - React / Vue 等のコンポーネントを島として利用可能
- 欠点:
  - インタラクティブなSPA（エディタ・リアルタイムプレビュー）には不向き
  - クライアントサイドの状態管理が煩雑になる

## 決定

**選択肢 A: Vite + React** を採用する。

認証不要・バックエンド不要のクライアントサイドSPAという制約において、Vite + React が最もシンプルかつ目的に合致する。Next.js の SSR/SSG は本プロダクトでは不要な複雑さであり、Astro はインタラクティブなエディタ用途に不向き。

## 影響

- **正の影響**: 最小限の構成で高速にMVP開発を進められる。React エコシステムの html-to-image 等をそのまま活用できる
- **負の影響**: 将来的にSEOやサーバーサイド機能が必要になった場合、フレームワーク移行の検討が必要になる
- **リスク**: 低い。SPAで完結する要件が変わらない限り問題にならない
