# データ永続化戦略

## コンテキスト

プロフィールカード作成サイトにおいて、ユーザーが入力したカードデータをどのように保存するかを決定する必要がある。以下の制約がある:

- ユーザー認証なし
- バックエンド / データベースなし（クライアントサイド完結）
- ブラウザを閉じてもデータが残ることが望ましい
- MVPではシンプルさを最優先

## 検討した選択肢

### 選択肢 A: localStorage

- 利点:
  - 最もシンプルで実装コストが低い
  - 同期APIで扱いやすい
  - Zustand の persist ミドルウェアで透過的に永続化できる
  - 5MB程度の容量があり、テキストデータのみの本ユースケースには十分
- 欠点:
  - ブラウザ/端末をまたいだデータ共有ができない
  - ユーザーがストレージをクリアすると消失する
  - 構造化データのクエリには不向き（今回は不要）

### 選択肢 B: IndexedDB

- 利点:
  - 大容量データに対応
  - 構造化データの格納・クエリが可能
  - 非同期APIで大量データ処理時にUIをブロックしない
- 欠点:
  - APIが複雑で実装コストが高い
  - MVPのデータ量（1カード分のテキスト）には過剰
  - ライブラリ（Dexie等）を追加する必要がある

### 選択肢 C: Cookie

- 利点:
  - サーバーへの自動送信が可能（将来的にバックエンド追加時）
- 欠点:
  - 容量制限が厳しい（4KB）
  - カードデータの格納には不十分
  - 設定・操作が煩雑

## 決定

**選択肢 A: localStorage** を採用する。

MVPのデータ量（1枚のカード分のテキストデータ）には localStorage で十分。Zustand の persist ミドルウェアと組み合わせることで、ストアの状態を自動的に localStorage に同期できる。

データスキーマにはバージョン番号を持たせ、将来的なマイグレーションに備える。

## 影響

- **正の影響**: 実装コストが最小。Zustand persist で透過的に保存・復元される
- **負の影響**: デバイス間のデータ同期不可。ブラウザデータ削除で消失
- **リスク**: ユーザーがデータ消失を予期しない可能性がある → UI上で「データはこのブラウザにのみ保存されます」と明示する
